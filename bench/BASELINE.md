## Notes / anomalies

- **Bulk echo transfers are intermittently UNRELIABLE on this build/machine.**
  Observed failure modes across pre-baseline probes and this run:
  (a) a stall — throughput collapses to ~0.2 MB/s and the transfer crawls or
  never finishes (rc=timeout); (b) a truncated tail with an early EOF — the
  echo comes back 8-48 KiB short (short read). These hit **every**
  algorithm (first seen with zstd, then with plain none), occur in bursts
  (minutes where every attempt fails, then everything healthy again), and are
  not reproduced by an identical invocation minutes later. A healthy full
  bench2 pass takes ~2 s. The harness retries each bench2 invocation up to 5
  attempts (60 s timeout each) and keeps failed attempts as
  `<run>.log.attemptN`; bench2 retries needed for this baseline: **0**.
- Successful zstd runs show high run-to-run variance (see per-run values in
  the throughput table).
- Each throughput algo is measured in its own bench2 process (3 runs each), so
  a retry never re-measures the healthy algos.
- Watch→push latency includes the daemon's fixed 700 ms change-settle debounce
  plus a full 3000-file rescan; poll granularity ≈ 50 ms.

## Addendum — sync follow-up measurements (manual re-runs, 2026-09-22 13:2x)

Same recipe as the harness, run manually right after the baseline to pin down
the slow full pass (which is reproducible, not a one-off):

| Scenario | Wall time | Effective rate |
|---|---:|---:|
| 3000-file tree (232 MiB), full pass (re-run) | 184.77 s | ~1.25 MiB/s, ~62 ms/file |
| 20 × 10 MiB files (201 MiB), full pass | 30.46 s | ~6.6 MiB/s |

Even with few large files the sync engine tops out at ~6.6 MiB/s — ~60x below
the tunnel's 400+ MB/s single-stream echo — and small files add ~62 ms each of
per-file cost (manifest diff, request, tmp+rename, mtime set). The sync-layer
throughput, not the mux/compression path, dominates sync pass time. The
baseline run's 304.53 s full pass additionally hit the intermittent slow mode
described above (files arrived in bursts over ~5 min).

## Intermittent degraded windows — environment investigation (2026-09-22)

Symptom: zstd 16MiB echo intermittently drops to ~265-440 MB/s (healthy ~640-800),
sync full passes occasionally 63-185s vs healthy 5.5s. Sub-second granularity.

Hypotheses tested and ELIMINATED (each with a controlled comparison):
1. Power plan — already "High Performance" (8c5e7fda...). Not a factor.
2. Windows Defender real-time scanning — service not running (0x800106ba).
3. Tencent PC Manager direct CPU interference — present (QQPCRTP/QQPCTray) but
   its CPU delta is ~0 during degraded samples.
4. Thermal/turbo throttling — CPU % Processor Performance stays 193-200%
   (full turbo) during degraded runs.
5. E-core scheduling of compression threads — pinning to the first 8 logical
   cores (0xFF) did NOT remove variance; it made it worse (313-623 MB/s),
   disproving core-class scheduling as the cause.

Conclusion: host-level scheduling/memory-bandwidth jitter from background system
activity (driver DPCs, services, LLC contention on this 8P+16E laptop SoC).
Not an ectun code path — A/B builds slow down together. No code-level mitigation;
deployment guidance: avoid co-locating with heavy IO/CPU tasks, and use process
priority (High) if consistency matters more than peak throughput. Windows-only
observation; the LXC/Linux containers showed no such windows.
